# 01｜立项与师生选型

> 系列：[总览](00-总览-蒸馏关键环节与学习路线.md)
> 阅读时间：约 12 分钟
> 回答的问题：什么时候该蒸馏？教师、学生怎么选？容量差距怎么处理？

---

## 一、先回答"要不要蒸馏"

蒸馏解决的问题是：**用小模型以可接受的质量损失换取成本/延迟/部署优势**。但它不是唯一手段，立项前应把四个方案摆在一起比较：

| 方案 | 适用条件 | 主要成本 | 主要风险 |
|---|---|---|---|
| 直接调 API（教师直用） | 流量小、延迟不敏感、无私有化需求 | 每 token 费用 | 数据出域、成本随流量线性涨 |
| 微调开源模型（无教师） | 有高质量标注数据 | 标注 + 训练 | 数据量不足时天花板低 |
| 蒸馏 | 无标注但教师能做对；需要过程/行为能力 | 教师调用 + 验证 + 训练 | 教师错误传播、能力覆盖不全 |
| 路由/级联（小模型+升级） | 任务难度分布两极分化 | 路由器建设 | 漏升级、体验不一致 |

三个快速判据：

1. **教师在目标任务上的真实正确率**（抽 200–500 题实测，不看榜单）低于 80% 时，蒸馏的上限就是这个正确率乘以你的验证器召回，通常不值得做；
2. **月请求量 × 单价** 算出来的 API 成本如果低于一次蒸馏项目的总成本（教师调用+GPU+人力，通常数万美元级起步），先用 API + 路由；
3. 需要**私有化部署、低延迟（<500ms 首 token）或超高吞吐**时，蒸馏几乎是唯一选项，此时问题只剩"怎么做好"。

Distillation Scaling Laws（Apple, 2025）给出一个反直觉结论：如果教师本身也要为此专门训练，那么在很多算力配比下**直接训练学生比"先训教师再蒸馏"更划算**；蒸馏的经济性主要来自"教师已经存在"（现成 API 或已训好的开源模型）。工程含义：**永远优先用现成教师，不要为蒸馏专门养教师**。

## 二、学生选型：先定部署约束，倒推规模

顺序不能反——不是"选个学生再看能不能部署"，而是：

```text
目标硬件与延迟/吞吐指标
→ 允许的参数量区间（含量化后）
→ 该区间内选基础能力最强、生态最好的底座
→ 再验证 tokenizer/模板与教师的兼容性
```

2026 年时点的实用建议：

- **底座优先级**：同等规模下选"指令跟随和工具调用已经不错"的底座（如 Qwen3 系列、Llama 3.x 系列），蒸馏是放大既有能力而非从零创造。底座本身工具调用格式混乱的话，Agent 蒸馏事倍功半；
- **规模的经验区间**：抽取/分类/格式转换 0.5–3B；领域问答+简单推理 4–8B；多步推理和 Agent 任务 8–14B 起，再小的模型轨迹能力天花板明显；
- **上下文窗口**要按 Agent 轨迹长度选：一条 20 步的工具轨迹很容易超过 16k token；
- **许可证**：确认底座许可允许商用及蒸馏衍生（注意某些 API 服务条款禁止用输出训练竞争模型——这属于合规红线，见 `07`）。

## 三、教师选型：可靠性 > 规模

教师的效用不是它的榜单分数，而是：

```text
Utility(教师) = 目标任务实测正确率
              × 输出的可学习性（学生能否吸收）
              × 接口兼容性（tokenizer/模板/logits可得性）
              − 单位成本
```

### 3.1 容量差距（capacity gap）

教师远强于学生时，学生效果反而可能下降——教师给出的推理粒度、知识依赖和分布复杂度超出学生容量。多项研究（Capacity Gap 系列工作）观察到"最适教师规模"随学生规模移动，并非越大越好。

实操上不必纠结理论：**拿 2–3 个候选教师，对同一批问题各生成一份验证后数据，各训一个小规模探针（比如 1k 样本 LoRA），看隔离集表现**。一天可以完成，比任何理论预测都可靠。

缓解容量差距的四个手段（可组合）：

1. 选中等教师或加"助教"中转（大教师→中模型→学生）；
2. 压缩监督：让教师输出简洁版推理而非完整长 CoT；
3. 课程化：先易后难分批训练；
4. on-policy 化：让教师在学生自己的生成上给反馈（见 `05`）。

### 3.2 黑盒还是白盒

| 教师类型 | 能提供 | 适合 |
|---|---|---|
| 闭源 API（GPT/Claude/Gemini） | 文本、多采样、部分 top logprobs | 答案/轨迹蒸馏，质量上限高 |
| 开源强模型本地部署（DeepSeek、Qwen 大杯） | 文本 + 完整 logits + 无限采样 | token 级 KD、on-policy、大批量生成（成本可控） |
| both：API 出难题的金标准，开源教师走量 | — | 多数实际项目的最优解 |

白盒 token-KD 要求教师学生 tokenizer 一致（或做跨词表对齐，成本高、收益不确定）。**如果教师学生不同家族，直接放弃 token-KD，做序列级蒸馏**，这是 2026 年仍然成立的工程默认值（跨 tokenizer 方法如字节级接口、GOLD 等在进步，但先建序列级基线再说）。

### 3.3 聊天模板是隐形接口

即使 tokenizer 相同，system/tool 消息格式、stop token、reasoning 段边界的差异都会造成训练-推理错位。规则只有一条：**所有训练数据以学生运行时的模板渲染**，教师的原始协议在数据编译时全部转换掉。

## 四、多教师：分工与仲裁

多教师的价值是**互补与复核**，不是投票。可靠性排序：

```text
客观验证器（执行/规则）
> 领域实测胜率高的专家教师路由
> 独立教师交叉复核（生成者≠批评者）
> 校准过的 LLM 仲裁
> 多数投票（最弱，共享偏差时失效）
```

起步阶段的建议编制：**1 个主教师 + 1 个批评/复核教师** 就够。教师路由表（每个教师在哪些能力单元上实测多少胜率、多少成本）等到单教师闭环跑通后再建。

教师意见冲突时：有验证器听验证器的；没有则看谁在自己专长域内；仍无法仲裁的进人工池并保留分歧记录——这些分歧样本本身就是高价值评测题。

## 五、常见坑

1. **用榜单分选教师**。榜单分布≠你的任务分布，永远先抽样实测。
2. **为蒸馏专门训教师**。经济性通常不成立（见 Scaling Laws）。
3. **学生选了小众底座**。工具调用模板、推理框架支持、量化生态都会成为后续每一步的摩擦。
4. **忽略服务条款**。用某些商业 API 的输出训练模型可能违反 ToS，立项时就要过法务，而不是训完再说。
5. **教师版本不固定**。API 教师悄悄升级会让数据分布漂移且不可复现；记录教师快照版本（如 `gpt-x-2026-05-13`）是数据 schema 的必填字段。

## 六、进一步学习（小综述）

**关于"蒸馏是否划算"**：
- [Distillation Scaling Laws](https://arxiv.org/abs/2502.08606)（Apple, 2025）——教师/学生算力配比的系统研究，回答"什么条件下蒸馏优于直接训练"。读结论部分即可。

**关于容量差距**：
- [Lifting the Curse of Capacity Gap](https://aclanthology.org/2023.acl-long.249/)（ACL 2023）——容量差距现象的早期系统分析与渐进迁移方案。
- [Towards the Law of Capacity Gap](https://aclanthology.org/2025.acl-long.1097/)（ACL 2025）——教师-学生规模的非单调关系的量化刻画。

**关于教师-学生工程实践**：
- [MiniLLM](https://arxiv.org/abs/2306.08543)、[GKD](https://arxiv.org/abs/2306.13649)——虽是训练算法论文，但其实验部分展示了不同规模师生组合的实测差异，是选型直觉的好来源。
- [DeepSeek-R1](https://arxiv.org/abs/2501.12948) 第 4 节——公开的"一个强教师 × 多规模学生（1.5B–70B）"蒸馏结果，可作为不同学生规模能到什么水平的参照系。

**关于跨架构/跨 tokenizer**（暂时只需要知道存在）：
- GOLD（cross-tokenizer on-policy distillation，已有 TRL 集成）、字节级接口方案 [Byte-Level Distillation](https://aclanthology.org/2026.customnlp4u-1.9/)——需要跨家族 token-KD 时再深入。

## 七、一页结论

```text
教师现成、实测正确率高 → 才值得蒸馏
部署约束 → 学生规模 → 生态最好的底座
教师选"实测可靠 + 学生学得动"，不选"最大"
2-3 个候选教师跑探针实验，一天出结论
同家族才做 token-KD，跨家族做序列级
起步 1 主教师 + 1 复核教师，版本全部固定并记录
```
